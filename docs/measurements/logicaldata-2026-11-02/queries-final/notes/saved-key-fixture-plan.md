# Третий случай: прежние сохранённые 4m keys

Это план, fixture ещё не создан и storage не изменён. Не использовать прежний raw как будто в нём уже есть actual POOL/USED queries.

1. Сначала два независимых fresh qlogicalexport на одной новой immutable final high/ru/district0 сборке, с одним frozen init/fixture/eval descriptor, но своими изолированными process/session/profile. Оба проходят startup actual Go/W и functionalQueries; никакой автоматической второй попытки при ошибке. Offline сравнить весь ordered actual transcript realAddress/levels/home/POOL и deterministic rows/refs proofs; elapsed/host timestamps не сравнивать на равенство. Snapshot и query transcript сравнивать отдельно.
2. После 2 PASS выбрать из ПЕРВОГО ИЗМЕРЕННОГО `functionalQueries.pool` ровно четыре разных существующих `actual.key`. Приоритет представительности: raw-door-front, generated-door-front, path spot, negative-coordinate spot. Категория определяется actual sourceSPOTSindex/координатами и ordered entrances; не обещать все категории в district0. Если категории нет, добавить первую ещё не выбранную key по фиксированным позициям pool 0, floor(n/3), floor(2n/3), n−1, затем по исходному порядку. Не создавать искусственные координаты. Каждый выбор хранит actual pool index, sourceSPOTSindex, x/z, entr/zone/d, raw/generated/path witness и independently computed round(x/4).toString(36)+'.'+round(z/4).toString(36).
3. Пятый valid legacy key выбрать из ИЗМЕРЕННОГО `logical.addresses.spots` вне actual pool key set: первый такой SPOT в исходном порядке (предпочтение другой настоящий district, если измеренный output позволяет классифицировать без копии DIST). Это реальный адрес города, исключённый текущим runtime pool; не произвольная строка. Выбор проверяет независимую 4m формулу и отсутствие key во всех actual pool rows, а не только отсутствие координаты. Если ни одного такого witness нет — сообщить blocker и не выдумывать fixture.
4. Не менять исходный high fixture. Root после отбора создаёт новый отдельный fixture того же формата/полной исходной карьеры и меняет ТОЛЬКО значение `dlv-used-addr` на `[key1,key2,key3,key4,legacyOutsidePool]` в этом порядке. Pin отдельные fixture SHA и таблицу происхождения каждого ключа, SHA raw обеих опорных процессов и final source/build/init/eval. Любое отличие остальных fixture key/value — fail подготовки. Никаких live setStore/reloadUsed/clearUsed/force/delivered.
5. Третий cold process запускается на ТОЙ ЖЕ immutable build, штатный Go/W. `functionalQueries.rawSavedUsed` и actual `ORDM.DEBUG.USED` должны точно повторить список из пяти строк до/после readonly queries; первые четыре связываются с actual pool index sets, пятый остаётся в USED и Store с пустым poolIndices. Не требовать уникальности pool keys: разные SPOTS одной 4m клетки — допустимая legacy коллизия; quarter-metre `entr` classification проверяется отдельно.
6. Geo/catalog/actual query transcripts должны совпасть с fresh cases (кроме saved used mappings и разрешённых career/runtime наблюдений, явно перечисленных в gate). Если старый список неожиданно влияет на geometry/RNG/query output, сохранить первый FAIL и расследовать, не ослаблять сравнение и не объявлять USED noninput заранее.

Граница доказательства: загрузка прежнего ordered persisted key list и совместимость с текущим runtime pool; не выбор следующего заказа, не markUsed/старение и не доставка. Сохранения автора не читаются; ни одной fixture записи в этом задании не выполнялось.
